Disclosure, not judgment

AI now helps write a great deal of code. Colophon gives anyone reading that code a clear, consistent answer to a simple question: how did AI contribute, and did a person check the result?

Why disclose AI use in code

People read code for many reasons. A maintainer decides whether to merge a change, a reviewer looks for what might break, a student learns from an example, and a user decides whether to depend on a library. Each of them reads the code differently depending on how it came to be.

“Made with AI” says almost nothing about that. AI may have suggested an approach, written one helper function, drafted a whole feature, or produced the entire test suite. A person may have rewritten everything it produced, or accepted it after a careful review, or not checked it at all. These are very different situations, and the reader of the code rarely gets to know which one applies.

A colophon is the note at the end of a book that records how it was made. Colophon aims to make the same kind of note a normal part of sharing code. It is not tied to one tool, language, or platform. A compact badge states where AI contributed, how much of the result it shaped, and whether a person reviewed it. A short written disclosure next to the badge supplies the details.

Free text alone is hard to compare and easy to leave vague. A shared scale lets readers see at a glance what kind of change they are looking at, and the written disclosure keeps the nuance.

What Colophon stands for

A score describes origin, not quality

A 4 is not a warning and a 0 is not a merit. Well-reviewed AI code can be excellent, and hand-written code can be poor. The scores say who produced the work, not whether it is good.

Credit where it is due

Disclosure works both ways. If AI did a remarkable job, say so. Readers learn what AI handles well, and the people who guided it get credit for that too.

Unreviewed code is a red flag

Review is reported separately from AI use, and it is the one place Colophon does judge. Fully delegated work can earn the green check. Code nobody checked gets a red cross, even if a person wrote all of it.

Honest beats precise

Colophon is a self-declaration, not a detection tool. When you cannot establish what happened, ? is a better answer than a confident guess.

What Colophon can’t do

  • It can’t verify anything. A colophon is the author’s declaration. Readers can weigh it against the written disclosure, the commit history, and review records, but no tool can confirm it.
  • It can’t stop judgment. Some readers will distrust a 4 or doubt a 0. Colophon makes the facts clear and consistent; how they are received is up to the reader. Where a project discourages AI, there is a pull toward under-reporting, and an honest ? beats a wrong 0.
  • It doesn’t ask for your prompts. The evidence you score from, such as chats and agent logs, stays private. The disclosure states conclusions, not transcripts.
  • It describes one scope at a time. A badge covers the scope named next to it, such as the latest release, not the whole history of a project.

Disclosure is not licensing

A colophon describes how code was made. A license describes what others may do with it. The two answer different questions, and a Colophon badge neither grants nor restricts any rights. A project with a 4 in every category still needs a license, and a license says nothing about how the code was produced.

AI-generated code can raise legal questions of its own, such as who holds the copyright in AI output and whether generated code reproduces licensed material. Colophon does not answer them, and the rules differ between jurisdictions. Check your organization’s policy and the contribution guidelines of the projects you work on. Some projects restrict or refuse AI-generated contributions.

For licensing itself, these resources are a good place to start:

  • Choose a LicenseA plain-language guide to picking an open-source license, maintained by GitHub.
  • SPDX License ListStandard identifiers, such as MIT or GPL-3.0-or-later, for package metadata and file headers.
  • REUSEA specification and tool from the FSFE for declaring the copyright and license of every file in a project.
  • OSI Approved LicensesThe licenses the Open Source Initiative has reviewed and approved as open source.

Read the badge

Four cells score AI’s contribution to one scope, such as a pull request or a release. From left to right they cover Design, Implementation, Tests & checks, and Comments & docs. The person icon shows the human review status, and the final cell flags it: green for Full, amber for Partial, red for no or unknown review.

Each category is scored from 0 None to 4 Delegated, with ? when the evidence does not settle it and – when the scope has no work in that category. The scoring guide explains every category and score with examples, and the home page has a labelled diagram of the badge.

Write a disclosure

The badge gives the summary at a glance. A few sentences under it tell the reader what the scores refer to. Put the disclosure where readers of that scope will look: an “AI disclosure” section in the README for a project or release, or the description of a pull request. The self-assessment fills in the template below for you.

What to cover

  1. Scope. The pull request, release, or set of changes the badge describes.
  2. What AI contributed. Name the parts: modules, functions, test files, or documents. Say whether AI advised, wrote pieces, drafted, or delivered them. Naming the tool can help readers but is optional.
  3. What people did. The decisions, specifications, rewrites, and parts written without AI.
  4. How it was checked. The checks actually performed, such as reading the diff, running the tests, or comparing the docs with the code’s behavior. Say which ones were run and which were inspection only, and whether the review was the author’s own or independent.
  5. Worth noting Optional. Where AI did notably well or poorly, and anything a reader of the code should keep in mind.

Template

## AI disclosure

[![Colophon badge](<badge URL>)](<rubric URL>)

**Scope:** PR #42, retry handling for the job queue.

**What AI contributed.** …

**What people did.** …

**How it was checked.** …

**Worth noting.** …

Keep a blank line between parts. On GitHub, lines without a blank line between them run together into one paragraph.

Examples

Tips

  • Be specific. “AI wrote the parser tests” helps the reader. “AI was used responsibly” does not.
  • Report only checks you ran. Reading a diff and running the tests are both worth reporting, but say which one you did.
  • State what you don’t know. If a contributor’s AI use is unclear, say so and use ?.
  • Keep the tone factual. No apology and no boasting. Describe what happened.
  • Keep it current. When the scope changes, such as a new release, update the badge and the text together.

Frequently asked questions

Which scope should a badge in my README use?
Usually the latest release. Name the scope in the disclosure and update both when you release again. For a pull request, put the badge in its description.
Does editor autocomplete count?
Yes. Count every AI use you know of. Completions inside code you were writing are usually a 2; see the edge cases in the scoring guide.
How does this relate to commit trailers such as Co-authored-by?
Trailers such as Co-authored-by record which tool or person touched a commit. A colophon summarizes how much AI shaped a whole change and whether a person checked it. The self-assessment also gives you a Colophon: trailer, such as Colophon: v1 D3 I4 T4 C- review=full, so tools can read the disclosure from your history.
What happens when the rubric changes?
Each badge links to its rubric version’s page, which explains what that badge says. Badges for that version never change. A new version gets new badge paths.
Is Colophon related to the AI Disclosure (AID) Framework?
No. Kari Weaver’s AID Framework is a disclosure standard for research writing. Colophon covers code. An early version of this project was also called AID and was renamed to avoid confusion.
How can I give feedback?
Colophon is an open project. Suggestions, criticism, and examples from your own projects are welcome as GitHub issues.
